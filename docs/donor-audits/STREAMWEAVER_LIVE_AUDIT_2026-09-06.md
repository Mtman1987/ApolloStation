# StreamWeaver → ApolloStation functionality audit

Audit date: 6 September 2026 (UTC). Scope: StreamWeaver only, the first app shown in the supplied `mtman-new` Fly organization screenshot.

## Decision

**StreamWeaver is not ready for a functionality-preserving swap to ApolloStation.** This source-level audit identifies **18 absent capability groups** and **21 partial or unwired groups**, with 19 existing/equivalent areas credited below. These are grouped findings, not counts of unique user actions or severity scores. Some groups overlap at a dependency such as speech.

The complete authenticated live acceptance audit remains open. This report combines a verified live revision, reconstruction of deployed source transformations, repository-wide comparison and a route/page inventory. It does not claim that every live tenant setting, external provider operation or UI interaction has been exercised.

- ApolloStation audited main: `3c195e63b7c0648efde40d40b897d3c2004e7815`. Working tree remained clean. No changes, commits, pushes or deployments were made for this audit.
- StreamWeaver origin/main was `5903b14b31c017402c091bddf2c5cbbe1da4dd56`; its only difference from the deployed revision was a CI decoder-install adjustment. The audit uses the actual live revision, not that later head.
- The donor checkout had pre-existing uncommitted edits. Those were preserved and excluded. The deployed revision was extracted to an isolated snapshot; all 12 source patch scripts called by the image build were replayed successfully there. This reconstructs effective source; it is not an extraction of the running container.
- Inventoried **216 route-handler files** and **65 page files**. Route counts include auth/redirect/internal/debug surfaces; they are not unique feature counts. The full manifest is appended.
- Compared `apps/` and `packages/` across Apollo, including StreamWeaver, Chat Gateway, Commlink, Stellar, HearMeOut, DSH, Nebula, MountainView, Companion, shared contracts and authority. Checked runtime construction and request handling, not just names, exports, tests or capability manifests.
- The app root redirected to login; `/api/version` returned 401. Authenticated live UI, Fly machine/volume configuration, private tenant files, credentials and downstream runtime health were not available. A health response does not establish provider success.
- Source links are pinned to the original commit. Where build scripts modify a linked file, the reconstructed version was considered; the GitHub link shows its committed input. See the build-patch appendix.

## How to read the findings

**Absent:** no equivalent implementation was found in the audited Apollo apps/packages after tracing the closest counterpart. **Partial:** useful code or an equivalent foundation exists, but a required service, producer, UI, adapter or persistence path is missing/unwired. These describe source evidence, not live configuration. **Existing:** code exists for the stated behavior; production acceptance still needs real connections and data.

The absence claims are bounded to this revision and repository. Undocumented externally deployed services could change the result, but none were verified as Apollo replacements in this audit.

## Legacy declarations are not proven live features

The old automation UI/registries list more operations than the actual engines execute. For example, the SubActionHandlers action-state method logs success with a TODO instead of updating ActionManager; server-side file handler branches also contain TODOs. TriggerRegistry entries for schedules, MIDI, filesystem changes, polls/predictions and other events are not sufficient evidence of a registered running trigger. They are excluded from the confirmed missing-feature list unless an actual source path was found.

The live graph really does implement custom scripts via `new Function` and TTS broadcast. Apollo deliberately uses bounded actions and safe expressions. Preserving useful workflows should use supported capabilities, not blindly restore unrestricted script execution. Evidence: [live graph](https://github.com/Mtman1987/streamweaver/blob/4cb3c654b7e2c7a88ae5ec63c246f9902cc781af/src/lib/flow-runtime.ts), [legacy handlers](https://github.com/Mtman1987/streamweaver/blob/4cb3c654b7e2c7a88ae5ec63c246f9902cc781af/src/services/automation/subactions/SubActionHandlers.ts), [Apollo runnable validation](https://github.com/Mtman1987/ApolloStation/blob/3c195e63b7c0648efde40d40b897d3c2004e7815/apps/streamweaver/src/flow-packages.ts).

Generic Games/activity pages, route descriptors, capability names, test fixtures and optional dependency interfaces were not counted as completed integrations. Conversely, shared implementations elsewhere in Apollo were credited instead of insisting on a same-name StreamWeaver page.
