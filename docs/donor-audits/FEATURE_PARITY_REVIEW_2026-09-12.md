# HearMeOut and Discord Stream Hub — Apollo parity and placement review

Prepared 12 September 2026; review decisions updated 13 September 2026. **All HMO and DSH items are now approved for implementation and subsequent live replacement.** Historical batch decisions and the superseding full approval are recorded below. This review document itself does not establish implementation or deployment completion.

There are **58 review rows in List 1** and **33 proposed work packages in List 2**. These are workflow groups, not counts of functions or new services. Every row and work package is approved. The implementation record tracks delivery separately from approval.

The most immediate HMO finding is that the current room Music/Watch panel displays and controls playback state but does not mount a media player. The separate Discord Activity page does mount one. Room state, a working microphone, and a “playing” label do not establish music/movie playback parity.

The review inventories live pages, HTTP routes, command handlers, worker endpoints, and startup/build patches, then traces Apollo entry points and consumers. The older 7 September DSH audit was a checklist, not the current baseline. DSH’s prebuild patches were read, not executed in its checkout.

This is a semantic source comparison, not a Git conflict report or a live acceptance test. No merge was attempted. Apollo and HMO have shallow histories, so absence of a local common ancestor would not prove unrelated histories. “Missing” below means no equivalent reachable implementation was found in the reviewed Apollo apps/packages. A source-wired feature can still need tenant configuration, provider access, saved data, and human acceptance.

## List 1 — what live has, what Apollo has, and what to do

**Present** = a reachable source path exists. **Shared** = the responsibility already belongs elsewhere in Apollo. **Partial** = some code exists, but behavior or wiring is incomplete. **Missing** = no equivalent implementation found. **Dependency** = Apollo still uses a live donor service. **Verify** = related code exists, but equivalence is not established. **Data** = reconcile saved state separately from code.

| Owner | Responsibility kept there |
|---|---|
| SPMT | Canonical users/tenants, links and credentials, XP ledger, shared events/presence and execution-job contracts. |
| HMO | Rooms, membership/admission/moderation, queue and playback state, room voice and media coordination. Elastic workers execute; they do not become room/database authorities. |

| Commlink + Chat Gateway | Shared chat history, destinations, generic forwarding and provider transport. |
| Stellar Core | Assistant reasoning, speech and memory; authorized Mission Control/Coder surface. Personal assistant state stays distinct from community room personas. |
| StreamWeaver | Persona configuration, automation and command routing into the owning app’s actions. |
| Nebula Arcade + shared media jobs | Existing games and reusable capture/render execution. DSH selects its community presentation and consumes results. |
| Workspace + Overlay Bay | Navigation, themes, saved scenes, Personal/Public outputs, popouts and renderer discovery. |

Public runtime configuration stays in managed volume JSON; revisioned app settings and domain state use their established stores. Secrets belong in the shared credential authority/secret provisioning path. Downloaded or user-owned media is classified independently from generated HLS/cache. These are implementation boundaries, not requests for new logins, keys, apps, or approval prompts.
